# Deploy & Doc Updater

> Skill for Stage 6 of the ticket-to-deploy workflow: generate/update deployment configuration, update knowledge base documentation, update Jira status, and post summary.

## Purpose

After the PR is approved and merged, finalize the ticket by: generating or updating deployment configuration, updating relevant knowledge base documents to reflect the changes, updating the Jira ticket status to Done, and posting a summary comment with links to all artifacts.

## Input

| Parameter | Required | Description |
|-----------|----------|-------------|
| `jira_key` | Yes | Jira issue key, e.g. `CBOL-123` |
| `pr_url` | No | GitHub PR URL (auto-detected if not provided) |
| `environment` | No | Target environment (default: `dev`) |

## Output

1. **Deployment config**: Updated Kubernetes manifests / Docker configs
2. **Knowledge base updates**: Updated docs in `01-CBOL-Domain-Knowledge/` and `02-Chat-Domain-Knowledge/`
3. **Jira update**: Status → Done, summary comment, labels
4. **Operation log**: `docs/operations/{JIRA-KEY}/06-deploy-v{N}.md`

## Workflow

1. **Read PR and merge status**:
   - Verify PR is merged
   - Get merge commit hash
   - Get PR body and changed files
2. **Generate/update deployment config**:
   - Read `01-CBOL-Domain-Knowledge/deployment-architecture/`
   - Read `01-CBOL-Domain-Knowledge/configuration/`
   - If new service/endpoint: update Kubernetes manifests (Deployment, Service, ConfigMap)
   - If config changes: update ConfigMap / application.yml
   - If database changes: update migration scripts
3. **Update knowledge base**:
   - If new domain entity: update `01-CBOL-Domain-Knowledge/domain-model/`
   - If new API: update `01-CBOL-Domain-Knowledge/api-definitions/`
   - If new DB table: update `01-CBOL-Domain-Knowledge/database-schema/`
   - If new module: update `01-CBOL-Domain-Knowledge/module-structure/`
   - If new pattern/approach: update `02-Chat-Domain-Knowledge/` relevant docs
   - If config changes: update `01-CBOL-Domain-Knowledge/configuration/`
4. **Update Jira**:
   - Transition status: `In Progress` → `Done` (or appropriate workflow transition)
   - Add labels: `ai-completed`, remove `ai-in-progress`
   - Post summary comment (from template above)
   - Link PR in Jira (if not already linked)
5. **Write operation log**:
   - Summary of deployment config changes
   - Summary of knowledge base updates
   - Jira update confirmation
   - Evidence (commands + output + exit code)

## Deployment Config Update Rules

### Kubernetes Manifests
- New service: create `k8s/{service-name}/deployment.yaml`, `service.yaml`, `configmap.yaml`
- New endpoint: update existing ConfigMap, no new Deployment needed
- Resource limits: follow existing patterns (CPU/memory requests/limits)
- Health checks: always include livenessProbe and readinessProbe
- Environment variables: use ConfigMap references, never hardcode secrets

### Configuration
- New config keys: add to `application.yml` with default values
- Document new keys in `01-CBOL-Domain-Knowledge/configuration/`
- Sensitive config: use Kubernetes Secrets, not ConfigMap

### Database Migrations
- New tables: create migration script in `src/main/resources/db/migration/`
- Follow Flyway naming: `V{version}__{description}.sql`
- Include indexes (reference Turms index design)
- Include rollback script if possible

## Knowledge Base Update Rules

- **Only update if the change is durable and reusable** — one-off implementation details don't need KB updates
- **Update existing docs before creating new ones** — check if a relevant doc already exists
- **Follow existing doc structure** — match the format and sections of similar docs
- **Add references** — link to the PR, Jira ticket, and SDD in the updated doc
- **Mark AI-generated updates** — add a note at the bottom: `*Updated by AI workflow for {JIRA-KEY}*`
